0. THE BLANK SLATE (Image Management)
--------------------------------------------------------------------------------
We started with a completely empty machine and pulled our raw materials:

docker pull nginx:alpine       -> Download Nginx from Docker Hub
docker pull alpine:latest      -> Download a tiny Linux OS
docker images                  -> Verify they are saved on our hard drive

--------------------------------------------------------------------------------
1. THE DOCKERFILE AND MULTI-STAGE BUILDS
--------------------------------------------------------------------------------
We discussed how to write a Dockerfile, but more importantly, we covered the secret to small images: Multi-Stage Builds.

Why it matters:
If you build a Node/React app, you need `npm` to build it, which takes up 900MB. But you only need Nginx (20MB) to serve the final files!

The Solution:
# Stage 1: Build it
FROM node:18 AS builder
RUN npm run build

# Stage 2: Serve it (and throw away Node!)
FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html

Result: You get a tiny, fast 20MB production image instead of a 1GB monster.

How to actually build and share it:
docker build -t myapp:1.0 .          -> Tells Docker to read the Dockerfile and build the image locally.
docker push myrepo/myapp:1.0         -> Pushes your built image up to Docker Hub so servers can download it.

2. MASTERING DOCKER COMPOSE (The Blueprint)
--------------------------------------------------------------------------------
We started by writing the perfect docker-compose.yml file. 
You wrote this from scratch and nailed it:

version: "3.8"
services:
  postgres_db: 
    image: postgres:15
    ports:
      - "5432:5432"
    environment:
      - POSTGRES_PASSWORD=supersecret 
    volumes:
      - db_data:/var/lib/postgresql/data

  api_backend:
    image: nginx:alpine 
    ports:
      - "8000:80"
    depends_on:
      - postgres_db
    restart: unless-stopped 

volumes:
  db_data: 

THE LESSON: 
- `image:` downloads from the internet. `build: context:` builds from a local folder.
- `unless-stopped` is safer than `always` because it respects when a human types `docker stop`.
- You don't care if containers get deleted! Because the Compose file is the blueprint. Just run `docker compose up -d` and everything comes back to life.

--------------------------------------------------------------------------------
2. THE RAPID-FIRE COMPOSE DRILL
--------------------------------------------------------------------------------
We ran these commands in a rapid-fire sequence to see how Compose works:

docker compose up -d           -> Starts everything in the background
docker compose ps              -> See what is running for THIS project
docker compose logs            -> Spits out logs for both DB and API mixed together
docker compose logs -f api_backend -> Follow logs for just one service live
docker compose restart api_backend -> Reboot just the Node/Nginx server, not the DB
docker compose exec postgres_db bash -> Jump inside the DB container shell
docker compose down            -> Kills containers & networks (keeps volumes safe)
docker compose down -v         -> NUCLEAR OPTION: Wipes containers AND volumes (data lost!)

--------------------------------------------------------------------------------
3. THE MANUAL CONTAINER LIFECYCLE (run, ps, stop, kill)
--------------------------------------------------------------------------------
Before we relied purely on Compose, we proved we could do it manually:

docker run -d --name rogue-app alpine sleep 1000 -> Start a background container
docker ps                      -> Check it is running
docker stop rogue-app          -> Graceful shutdown (SIGTERM)
docker kill rogue-app          -> Violent immediate shutdown (SIGKILL)
docker ps -a                   -> View ALL containers, even dead ones
docker rm rogue-app            -> Clean up the dead container

--------------------------------------------------------------------------------
4. INSPECTION & DEBUGGING (Troubleshooting a Broken Container)
--------------------------------------------------------------------------------
We created a test container: `docker run -d --name my-test-app nginx:alpine`
Then we played DevOps detective:

docker logs my-test-app        -> Did it crash? Read the errors.
docker logs -f my-test-app     -> Watch the traffic hit it live.
docker exec -it my-test-app sh -> Break into the container's shell to look around.
docker inspect my-test-app     -> Spits out massive JSON config (IPs, networks).
docker stats                   -> Live dashboard of CPU and RAM usage.
docker top my-test-app         -> See exact processes running inside.

4. THE "MAGIC PHONEBOOK" DRILL (Docker Networking)
--------------------------------------------------------------------------------
You asked: "How is it possible for two isolated containers to communicate?"
The Answer: The Virtual Router and the Magic Phonebook (Docker DNS).

We proved it with this exact drill:
1. docker network create secret-lan
2. docker run -d --name backend-api --network=secret-lan nginx:alpine
3. docker run -it --name frontend-app --network=secret-lan alpine sh
4. Inside the shell, we typed: `ping backend-api`
5. The output showed `PING backend-api (172.18.0.2)`. 

THE LESSON:
Docker's hidden DNS server automatically translated the name "backend-api" into the secret IP address "172.18.0.2". This is how microservices talk securely without exposing ports to Windows.
NETWORKS = Communication in motion (Container to Container).

--------------------------------------------------------------------------------
5. THE "USB FLASH DRIVE" DRILL (Docker Volumes)
--------------------------------------------------------------------------------
You asked: "What is the purpose of Volumes? Do we store Nginx in it?"
The Answer: No, the software is in the image. Volumes are for DATA THAT CHANGES (like a database of users).

We proved Volumes act exactly like a USB Flash Drive with this drill:
1. docker volume create my-usb-drive
2. docker run -it --name worker-bot -v my-usb-drive:/data alpine sh
3. Inside the shell: `echo "This is my indestructible database!" > /data/secret.txt`
4. MURDER THE CONTAINER: `docker rm -f worker-bot`
5. Plug the USB drive into a NEW container: `docker run -it --name new-bot -v my-usb-drive:/data alpine sh`
6. Inside the new shell: `cat /data/secret.txt` -> The data survived!

THE LESSON:
VOLUMES = Data at rest (Container to Hard Drive). When the container dies, you still hold the USB drive in your hand.

--------------------------------------------------------------------------------
6. THE GRAND CLEANUP (Nuking everything)
--------------------------------------------------------------------------------
We learned that deleting an image DOES NOT delete your source code on Windows. You can always rebuild!

The cleanup commands we used:
docker rm -f container_id      -> Force kill a running container
docker rmi -f image_id         -> Force delete an image
docker container prune         -> Delete stopped containers
docker volume prune            -> Delete unused volumes
docker network rm mynet        -> Delete a specific network

THE ULTIMATE NUKE COMMAND:
docker system prune -a         -> Deletes everything unused (Stopped containers, dangling networks, and ALL unused images).

We hit a wall where Docker refused to delete Kubernetes images (`kindest/node`) because it said they were "In Use" (U). We learned we have to kill the containers using them first, or disable Kubernetes in Docker Desktop to free them up.

--------------------------------------------------------------------------------
8. THE FINAL MISSING COMMANDS & PRO-TIPS
--------------------------------------------------------------------------------
Before we leave Docker forever, here are the final few commands from our cheat sheet that we touched on:

docker compose up --build -d   -> If you change your code/Dockerfile, you MUST add `--build` so Compose knows to re-compile your image before starting.
docker rm -f container_id      -> The `-f` stands for FORCE. It violently kills and deletes the container in one single command so you don't have to `stop` it first.
docker image prune             -> Deletes only unused images (leaves networks/volumes alone).
.dockerignore                  -> Just like .gitignore, but stops massive folders (like node_modules) from being sent to Docker during a build, saving huge amounts of time.

PORT MAPPING RULE (-p 8080:80): 
Host port (Windows) is ALWAYS on the left. Container port is ALWAYS on the right.

--------------------------------------------------------------------------------
9. INTERVIEW THEORY (The "Gotcha" Questions)
--------------------------------------------------------------------------------
If you are doing a DevOps interview, they will try to trick you with these conceptual questions. We didn't do drills for these, but you MUST know them:

1. CMD vs ENTRYPOINT
- `CMD` is the default command, but a user can easily override it when they run the container (e.g., `docker run image bash`).
- `ENTRYPOINT` is strict. It ALWAYS runs, and you cannot easily override it.

2. COPY vs ADD
- Always use `COPY` to move files from Windows into the container.
- `ADD` does the exact same thing, but it has hidden magic: it can download from URLs and automatically extract `.tar.gz` files. Use it only when you need that magic.

3. RESOURCE LIMITS
If you don't limit a container, it can eat 100% of your host's RAM and crash your PC.
Always use limits in production: `docker run --memory="256m" --cpus="0.5" nginx`

4. SECURITY & SECRETS
- NEVER bake passwords or API keys directly into a Dockerfile or image (because anyone who pulls the image can read them). Pass them at runtime using `-e POSTGRES_PASSWORD=secret`.
- NEVER run your container as the `root` user in production. Create a restricted user (`USER appuser`) so if a hacker gets in, they don't have full admin rights.
